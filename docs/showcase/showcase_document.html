Operational fragmentation, lost medical histories, and paper records cause catastrophic economic losses.

Modular Monolith & Clean Architecture

Strict separation of presentation, business domain logic, and persistence abstractions in Java 21 LTS.

Layered Clean Architecture

Bounded Contexts & Modules

Domain aggregates (Animal, Appointment, MedicalRecord, DiseaseReport) are organized into isolated packages, preventing tight coupling and facilitating seamless future extraction if necessary.

Figure 7.1: Clean Architecture Inward-Pointing Dependency Flow in Vetra Backend

Standardized Envelopes

Every REST endpoint returns a uniform ApiResponse<T> structure with timestamp, status code, localized message, and payload.

Security Design • Section 10
10 — Security

Authentication, RBAC & Tenant Isolation

Zero-trust security architecture enforcing cryptographic token security, multi-tenant isolation, and secret protection.

Dual-Token Authentication (JWT)

- Access Tokens: Short-lived stateless HMAC-SHA512 JWTs (24h expiration) carrying principal ID and role authority claims.
- Refresh Tokens: Cryptographically secure 256-bit random tokens persisted in database with single-use rotation and revocation on logout.

Multi-Tenant Data Isolation

Every query against animal records, appointments, or medical documents is programmatically scoped to the authenticated user's ID (farmer.id = :farmerId). Cross-tenant queries return empty result sets rather than unauthorized data.

Figure 10.1: Cryptographic Authentication and Principal-Based Tenant Isolation Pipeline
Secret Management

Zero plaintext secrets in code. Environment variables and database credentials injected at container startup via AWS Secrets Manager.

Log Sanitization

Runtime interceptors redact Authorization headers, refresh tokens, and passwords from logs, preventing log storage leakage.

Automated Secret Scans

Gitleaks SAST scanner executes on every pull request in GitHub Actions, preventing accidental API key or credential commits.

Engineering Case Study • Section 12
12 — Technical Case Study

The PostgreSQL Animal Search Defect

How a subtle prepared-statement parameter deduction failure on PostgreSQL RDS was diagnosed and solved via Criteria API.

1. The Problem (Runtime PSQLException)

The animal search endpoint (/api/v1/animals/search) threw HTTP 500 when optional filter parameters were omitted. PostgreSQL JDBC driver failed prepared statement parameter deduction: PSQLException: could not determine data type of parameter $5.

2. Root Cause Investigation

The legacy static JPQL query used (:species IS NULL OR a.species = :species). Because PostgreSQL strictly types positional parameters ($X), passing Java null for custom enum and UUID types left parameter types indeterminate at plan compilation.

Figure 12.1: Animal Search Defect Investigation, Solution Architecture & RDS Verification
Live RDS Verification Across All 6 Permutations

Verified live against Amazon RDS PostgreSQL 15.13: (1) Tag-only, (2) Tag+Species, (3) Tag+Gender, (4) Species+Gender, (5) All 6 filters, (6) Omitted optional filters, and cross-farmer multi-tenant isolation. All tests returned 200 OK with exact entity counts.

Architecture Trade-Offs • Section 16
16 — Technical Rationales

Key Engineering Decisions & Trade-Offs

Architectural choices analyzed through technical requirements, trade-offs, and measured benefits.

1. Modular Monolith vs. Microservices

DECISION: Single deployable Spring Boot artifact with strict internal package boundaries.
REASON: Eliminates distributed network overhead, complex saga orchestrations, and high multi-service operational costs while preserving domain modularity.
BENEFIT: Instant transactional guarantees across clinical entities and sub-10ms inter-module calls.

2. Java 21 LTS & Spring Boot 3.5.16

DECISION: Enterprise Java 21 runtime with Spring Boot 3.5.16 framework.
REASON: Provides mature ORM ecosystem (Hibernate 6), robust concurrency, strong type safety, and enterprise longevity.
BENEFIT: High-throughput clinical record processing with zero compile-time type ambiguities.

3. Flutter Cross-Platform Client

DECISION: Single Dart codebase targeting Android and iOS.
REASON: 100% UI and business logic sharing between mobile farmer and veterinary personas.
BENEFIT: Accelerated release cycles, unified network interceptor pipeline, and identical offline storage behaviors.

4. Dynamic JPA Specifications

DECISION: Replaced static JPQL optional filter query with Criteria API Specifications.
REASON: PostgreSQL fails prepared statement type inference on omitted null enum parameters.
BENEFIT: Clean SQL generation with only non-null predicates; 100% test pass on Amazon RDS PostgreSQL.

5. Multi-Agent AI Gateway

DECISION: Decoupled AI execution into immutable gateway pipeline and specialized agents.
REASON: Prevents tight coupling to vendor LLM SDKs and enforces safety and cost budgeting.
BENEFIT: Seamless fallback to NoOp in tests and zero code changes when changing AI models.

6. AWS ECS Fargate & Terraform

DECISION: Serverless container tasks orchestrated via modular Terraform IaC.
REASON: Eliminates EC2 server patching and Kubernetes control-plane complexity while providing instant Multi-AZ scaling.
BENEFIT: Declarative, repeatable staging and production environments with zero manual AWS clicks.
