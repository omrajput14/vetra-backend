Engineering Principles • Section 01
01 — Cloud Engineering Philosophy

Infrastructure Principles & Design Philosophy

Architecting veterinary operations for high availability, zero-trust network isolation, and immutable automation.

"Cloud infrastructure for rural and agrarian medicine must satisfy two competing requirements: extreme cost efficiency during development and enterprise-grade resilience during epidemiological outbreaks. In Vetra, infrastructure is treated strictly as reproducible software code. We enforce complete separation between staging and production, eliminate shared database access, and mandate automated cryptographic zero-trust boundaries across every network hop."

— Om Rajput, Cloud Architect
1. Declarative IaC

Every AWS resource (VPC, ECS, RDS, Redis, IAM) is managed through modular Terraform scripts with remote S3 state and DynamoDB locking.

2. Zero-Trust Isolation

Three-tier subnet segmentation: Public (ALB/NAT), Private (Fargate tasks), and Isolated (RDS/Redis with zero public internet routing).

3. Immutable Releases

Container images are built via multi-stage Docker builds, tagged immutably with Git commit SHAs, and deployed with zero downtime rolling updates.

Terraform Engine • Section 05
05 — Terraform Architecture

Infrastructure as Code: Modular Terraform Engine

Reusable infrastructure components, state locking, and strict separation between staging and production.

Terraform Module Hierarchy

- infra/modules/vpc: VPC, public/private/isolated subnets, NAT/IGW.
- infra/modules/ecs: ECS cluster, Fargate task def, ALB, target groups.
- infra/modules/rds: RDS PostgreSQL 15, subnet groups, KMS keys.
- infra/modules/redis: ElastiCache Redis 7.1 with TLS.
- infra/modules/monitoring: CloudWatch 12 alarms, log groups, SNS.

Remote State & Concurrency Locking

Terraform state is stored in an encrypted Amazon S3 bucket with versioning enabled. State locks are acquired via Amazon DynamoDB table (vetra-terraform-locks) to prevent concurrent executions from corrupting cloud infrastructure state.

Representative Terraform Module Instantiation (infra/environments/staging/main.tf)
module "vpc" { source = "../../modules/vpc" environment = "staging" project = "vetra" aws_region = "ap-south-1" vpc_cidr = "10.1.0.0/16" availability_zones = ["ap-south-1a", "ap-south-1b"] public_subnet_cidrs = ["10.1.1.0/24", "10.1.2.0/24"] private_subnet_cidrs= ["10.1.10.0/24", "10.1.11.0/24"] isolated_subnet_cidrs=["10.1.20.0/24", "10.1.21.0/24"] enable_nat_gateway = true single_nat_gateway = true # Cost optimization for staging }
Environment Parameterization

Modules expose variables for CIDR ranges, instance types, task counts, and retention days, allowing identical module logic to power both staging and production.

Accidental Deletion Prevention

Database and storage modules utilize prevent_destroy = true lifecycle rules and automated final snapshots to protect clinical data against accidental destruction.

Subnet Segmentation • Section 06
06 — Subnet Segmentation

Network Architecture & Subnet Topology

Three-tier VPC subnet segmentation, routing tables, and internet gateway boundaries in ap-south-1.

Tier 1: Public Subnets

Attached to Internet Gateway. Hosts Application Load Balancers and NAT Gateways. Direct public internet ingress on ports 80 and 443 only.

Tier 2: Private Subnets

Hosts ECS Fargate container tasks. Inbound traffic allowed strictly from ALB security group. Outbound internet access via NAT Gateway.

Tier 3: Isolated Subnets

Hosts RDS PostgreSQL and ElastiCache Redis. No route to Internet Gateway or NAT. Inbound access restricted strictly to ECS security group.

Docker Architecture • Section 08
08 — Containerization

Application Containerization & Multi-Stage Dockerfile

Hardened minimal alpine image runtime, non-root user execution, and container JVM optimization.

Multi-Stage Build Pipeline

- Stage 1 (Builder): eclipse-temurin:21-jdk-alpine resolves Maven dependencies and compiles the Spring Boot fat JAR.
- Stage 2 (Runtime): eclipse-temurin:21-jre-alpine contains strictly the lightweight JRE, reducing attack surface and image size to ~180MB.

Runtime Security Hardening

- Non-Root Execution: Runs under dedicated unprivileged user spring:spring (UID 1001).
- Signal Handling: Uses dumb-init to properly forward SIGTERM signals for graceful Spring Boot shutdown.
- JVM Flags: -XX:MaxRAMPercentage=75.0 for container memory elasticity.

Hardened Production Dockerfile Architecture
# ── Stage 1: Build & Package ────────────────────────────────────────── FROM eclipse-temurin:21-jdk-alpine AS builder WORKDIR /workspace COPY pom.xml .mvn/ mvnw ./ RUN ./mvnw dependency:go-offline -B COPY src ./src RUN ./mvnw clean package -DskipTests -B # ── Stage 2: Hardened Runtime ───────────────────────────────────────── FROM eclipse-temurin:21-jre-alpine RUN apk add --no-cache dumb-init && addgroup -g 1001 -S spring && adduser -u 1001 -S spring -G spring WORKDIR /app COPY --from=builder --chown=spring:spring /workspace/target/*.jar app.jar USER spring:spring EXPOSE 8080 ENTRYPOINT ["/usr/bin/dumb-init", "--", "java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
Vulnerability Scanning on Push

Amazon ECR automatically scans container images on push (scan_on_push = true). Any Critical or High CVEs in base alpine packages are flagged before container deployment.

ECS Fargate • Section 09
09 — Compute Management

ECS Fargate Serverless Compute & Task Lifecycle

Zero-maintenance host management, Secrets Manager injection, and zero-downtime rolling deploys.

ECS Fargate Advantages

- Zero OS Patching: AWS manages underlying EC2 instances and hypervisor security.
- Per-Task ENI Isolation: Each task receives its own Elastic Network Interface (awsvpc mode) with dedicated private IP.
- Right-Sized Capacity: 0.5–1.0 vCPU and 1–2 GB RAM tailored to JVM memory allocations.

Rolling Deployments

- Minimum Healthy: minimumHealthyPercent = 100 guarantees that existing tasks serve traffic while new tasks launch.
- Maximum Surge: maximumPercent = 200 launches new task revisions in parallel before draining old revisions.

10 — Pipeline Automation

CI/CD Pipeline Engineering: Code to Staging

Automated build verification, secret leak scanning, container publishing, and live smoke tests.

1. Build & Test

Executes Java 21 compile, Google Checkstyle audit, and full Surefire test suite with an active Redis test container.

2. Secret Scan

Gitleaks scans full git history for API keys, AWS credentials, or database passwords before Docker build.

3. ECR Publish

Assumes IAM role via OIDC, builds image with GitHub Actions caching, and publishes immutable Git SHA tag to ECR.

4. Deploy & Smoke

Registers new ECS Task Def, triggers rolling update, waits for ALB target health, and runs 5 live HTTPS curl smoke tests.

PostgreSQL & PostGIS • Section 11
11 — Persistence Layer

Database & Data Infrastructure: RDS PostgreSQL 15

Spatial database engine, HikariCP connection management, and automated KMS-encrypted backups.

RDS PostgreSQL Configuration

- Engine: PostgreSQL 15.13 with native postgis and uuid-ossp extensions.
- Subnet Placement: Dedicated isolated DB subnet group across 2–3 AZs with zero internet routes.
- Storage: General Purpose SSD (gp3) with automated storage autoscaling and KMS encryption at rest.

Connection Pool Sizing (HikariCP)

- Maximum Pool: maximum-pool-size: 20 per ECS task.
- Idle Pool: minimum-idle: 5.
- Timeout: connection-timeout: 30000ms.
- Telemetry: HikariCP metrics instrumented via Micrometer and exported to CloudWatch.

Flyway Schema Migration Sequence (V1 to V14)

Schema migrations execute deterministically at application boot before accepting HTTP traffic. In staging and production, Flyway applies versioned SQL scripts (V1__extensions.sql through V14__refresh_tokens.sql), ensuring zero schema drift across environments.

Automated Backup Strategy

Daily automated snapshots retained for 1–7 days with Point-in-Time Recovery (PITR) enabled. Final snapshots are mandated on teardown.

Multi-AZ Standby Replication (Production)

Synchronous block-level replication to a standby instance in an alternate AZ with automated DNS failover completed in under 60 seconds.

Zero-Trust IAM • Section 13
13 — Zero-Trust Security

Infrastructure Security & Keyless OIDC IAM

Eliminating long-lived credentials via GitHub Actions OIDC and AWS Secrets Manager PrivateLink.

Keyless GitHub Actions OIDC

Vetra uses OpenID Connect (OIDC) federation between GitHub Actions and AWS IAM. No static AWS Access Keys or Secrets are stored in GitHub repository settings. Ephemeral STS credentials valid for 1 hour are granted strictly to refs/heads/main.

IAM Role Separation

- Task Execution Role: Pulls ECR images and resolves Secrets Manager values.
- Task Role: Grants running Spring Boot application least-privilege permissions to S3 buckets and CloudWatch metrics.

Production Architecture & High-Availability Safeguards

Multi-AZ elasticity, auto-scaling policies, and operational safety guardrails.

Production Status: [DRAFTED HA SPEC - NOT YET APPLIED]

db.t4g.medium with 100GB gp3 storage and synchronous Multi-AZ standby replication across 3 availability zones (a, b, c).

Engineering Safety Protocols
